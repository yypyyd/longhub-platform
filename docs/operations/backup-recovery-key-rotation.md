# 备份、恢复、密钥轮换与故障演练

> 历史/废弃：本文包含旧 Pack/知识库密钥与旧 Desktop 发布流程，仅作演练记录存档；不作为 clean-launch
> 首发部署或生产操作手册。当前流程以 `README.md`、Manager 架构和 Cloud Skill 生产门禁为准。

每次生产演练在隔离环境进行并记录操作者、时间、版本、RPO/RTO、校验摘要和结果。PostgreSQL 使用加密
存储的逻辑备份；恢复到新的隔离数据库后运行 migrations、行数/外键/租户抽样和 API 冒烟，禁止直接覆盖
生产。客户端发布物保留当前与上一稳定版，更新失败恢复签名前快照并启动旧安装器。

轮换顺序：先部署读取新旧公钥/密钥的版本，再切换签发或加密主密钥，再观察拒绝率，最后按保留策略
撤销旧密钥。模型 API Key 可逐策略替换，新请求使用新密钥，在途请求继续完成。Update 与 Pack key 不得
互用；数据库、模型、知识数据、设备凭据和 Authenticode 分开轮换。

知识数据密钥轮换不得原地猜测格式或复用模型密钥。先暂停知识写入，在隔离进程中用旧
`KNOWLEDGE_DATA_KEY` 逐条认证解密，以新随机密钥重新加密并校验 tenant AAD；完成行数、随机抽样和
失败清单核对后再原子切换数据库与服务密钥。首次从开发明文升级时，通过管理 API 导出业务源文件并
重新导入，确认所有 `content` 都以 `longhub-kb-v1:` 开头后才能启用生产流量；备份中的旧密文按保留期
销毁，旧密钥在恢复窗口结束后撤销。

故障演练覆盖 Cloud 断网、模型超时/429/5xx、主模型熔断与备用、数据库只读/不可用、磁盘不足、Gateway
强退、坏客户端更新、Pack 吊销和设备凭据泄露。失败时先紧急停用策略或暂停发布，再保留证据、恢复服务、
验证租户隔离，最后复盘。真实恢复演练需要生产同构数据库、KMS 和备份存储授权，不能由本地测试伪造。
